# Public eval baseline

A gold question set and its first measured baseline, built on the design docs
in `/Docs` (public, already tracked in this repo) — not the user's own
documents, which live outside git per the accuracy-milestone plan.

## What's here

- `gold.yaml` — 33 reviewed questions (single_fact, enumeration, table_lookup)
  drafted by `docket eval draft` and reviewed for correctness against the
  source docs. This is a starting slice, not the full ~105-question mix the
  plan calls for: it has no numeric, multi_doc, follow_up, out_of_corpus or
  revoked questions yet, and no hand-written hard cases.
- `baseline.json` — `docket eval report` output (machine-readable) at the
  commit noted below.
- `baseline-runs.jsonl` / `baseline-judged.jsonl` — the raw run records and
  judge verdicts that produced it, for `docket eval compare` against later
  checkpoints.

## Baseline (post-M2)

Reproduce with:

```
docket eval run --corpus ../Docs --gold eval-public/gold.yaml --split all --repeats 3 --out <out>.jsonl
docket eval judge --gold eval-public/gold.yaml --runs <out>.jsonl --cross-check --out <out>.judged.jsonl
docket eval report --gold eval-public/gold.yaml --runs <out>.jsonl --judged <out>.judged.jsonl
```

**Accuracy (judged): 100.0% (33/33), 95% interval 89.6%-100.0%.** Pass-all
repeats (all 3 of 3, not just majority): 97.0% (32/33).

By type: enumeration 100% (9/9), single_fact 100% (22/22), table_lookup 100%
(2/2). By split: dev 100% (18/18), test 100% (15/15).

Retrieval recall@8: 100.0%. Fact-in-context: 100.0%. Wrongful abstention:
0.0% (0/99). The one remaining run-level failure is `generation_error`, not
retrieval — retrieval_miss is now 0/0 (was 11/11 pre-M2).

Caveats, unchanged from before: N=33 is small (wide interval); these are
easy single-fact/enumeration/table_lookup questions with no numeric,
multi_doc, follow_up, out_of_corpus or revoked cases yet, so 100% here is an
**upper bound for this easy slice**, not a claim about the milestone target
— real accuracy on harder question types and on the user's own documents is
expected to be lower. This reviewer (Claude) is not independent of the
question drafter (also an LLM) — the plan's required ~30 user-labeled
calibration sample has not been done yet, so the judge is not yet certified
via kappa.

### Pre-M2 baseline (for reference)

Accuracy (judged) 87.9% (29/33) [72.7%-95.2%]; recall@8 81.8%;
fact-in-context 81.8%; wrongful abstention 5.1% (5/99); 11/11 classifiable
failures were `retrieval_miss` — which is exactly the FTS5 keyword-search
bug M2 fixed (queries ANDed every word of a natural question together, and
bare and/or/not in a question could be parsed as FTS5 operators, so
"What are the six user journeys defined in the PRD" returned zero FTS
rows). Not context truncation (fixed separately in M1) or the generation
model.

## Extended synthetic gold set (`gold-extended.yaml`)

`gold.yaml` above is easy: only single_fact/enumeration/table_lookup, and its
gold spans repeat across near-identical cover chunks. The extended set exists
so that follow-up rewriting, file-name scoping, numeric/aggregate routing and
reranking can be measured. It is **synthetic**: every file is generated by
`build_synthetic_corpus.py` for a made-up company (Tarnwick Provisions Pvt Ltd),
so ground truth is known by construction. For that reason it is **not** a
milestone population (`population: synthetic_public`; milestone runs need
`real_user_documents`), and a high score here says nothing about the user's own
documents.

- `build_synthetic_corpus.py` — deterministic generator (openpyxl, python-docx,
  python-pptx; literal numbers, no formulas, zip timestamps frozen so reruns
  are byte-identical). Regenerate with
  `.venv/bin/python eval-public/build_synthetic_corpus.py`.
- `corpus-synthetic/` — the generated files (9), one sub-folder per source:
  `finance/` (Revenue-FY2024-25.xlsx in INR, Revenue-FY2025-26.xlsx and
  Revenue-FY2025-26-Budget.xlsx in INR thousands, Expenses-FY2025-26.xlsx),
  `operations/` (Warehouse-Throughput-Q2.xlsx, Ops-Review-Q2-FY2025-26.pptx),
  `strategy/` (Board-Memo-Q2-FY2025-26.docx), `people/` (Team-Directory,
  Compensation policy; the source the revoked questions revoke).
- `gold-extended.yaml` — 55 questions, all `reviewed: true` (checked against the
  generated data), every gold span verbatim and unique in the indexed text.

Traps built into the data: near-identical workbooks with different values for
the same month; quarter-subtotal and TOTAL rows (naive summing double counts);
a hidden memo row that is not in the totals; units that differ (INR vs INR
thousands, stated in a header or only on a Notes sheet); a percentage column;
blank cells (not launched) versus literal 0 (stock-out); a deck and memo whose
numbers agree with the workbooks in places and differ in others (Q3 target
28.5 vs 28.0, September on-time delivery 92.9% vs 92.4%).
`Expenses-FY2025-26.xlsx` deliberately keeps a merged title row above the header
row: the xlsx parser takes the first non-empty row as the header, so its chunks
are labelled with the title instead of column names (questions on it say so in
`origin`).

Question types: numeric 24 (10 exact lookups, 9 derived with arithmetic, 5
scoped to a named file), table_lookup 5, multi_doc 9 (4 ambiguous-period
"which fiscal year?" questions plus 5 workbook/deck/memo questions), follow_up
6, out_of_corpus 8, revoked 3. The ambiguous-period questions are encoded as
multi_doc requiring both fiscal-year values because Docket has no clarify-first
behaviour yet; a future answer that asks which year is also acceptable.
Everything except the people/ documents is in the `dev` split (a multi-document
question forces its documents into one split); the people/ questions are
`test`, so use `--split all`.

Run it (no judge needed for numeric facts, which are decided by regex):

```
docket eval run --corpus eval-public/corpus-synthetic --gold eval-public/gold-extended.yaml --split all --repeats 1 --out <out>.jsonl
docket eval report --gold eval-public/gold-extended.yaml --runs <out>.jsonl
```

Regenerating the corpus changes nothing as long as the generator is untouched;
if you edit it, re-ingest and re-check every gold span (`spans_indexed` in the
run records must be true).

### Extended baseline (main at e52f2fd, 1 repeat, no judge)

Reproduce with the commands above. Recorded in `baseline-extended-runs.jsonl`
for `docket eval compare` against later checkpoints.

Strict regex accuracy 61.8% (34/55); an earlier identical run gave 63.6%
(35/55), so treat one question as noise (generation runs at default sampling).
By type: numeric 12/24, multi_doc 5/9, follow_up 2/6, table_lookup 5/5,
out_of_corpus 8/8, revoked 3/3. Retrieval recall@8 (any span) 68.2% (30/44),
fact-in-context 54.5%, wrongful abstention 36.4% (16/44), abstention recall
100%, revoked leaks 0. 19 of the 21 classified failures are `retrieval_miss`.

Why it fails: spreadsheet row chunks carry no period or fiscal-year text
("Month: Jul ..."), so "July 2025" questions retrieve notes, headers and
other-year rows; the fast path then abstains or answers from the wrong
workbook; follow-ups are searched literally; derived and multi-row numeric
questions depend on the top-8 chunks containing every needed row. This is the
measured starting point for Upgrade/05 (rewrite, query signals, numeric tools),
not a defect in the questions: every failure was read and confirmed to be the
system's. 100% on out_of_corpus and revoked says nothing about those features
beyond this synthetic set.

### Extended results after doc 05 steps 1-3 (1 repeat, no judge)

Recorded in `after-period-context-extended-runs.jsonl`. Steps: explicit answer
sampling, token-budgeted prompt and location lines (step 1), follow-up rewrite
(step 2), sheet/period context in spreadsheet chunks' indexed text (step 3).

Strict regex accuracy 81.8% (45/55), up from 61.8% at the baseline above. By
type: numeric 18/24, multi_doc 6/9, follow_up 5/6, table_lookup 5/5,
out_of_corpus 8/8, revoked 3/3. Retrieval recall@8 (any span) 88.6% (39/44),
up from 68.2%; wrongful abstention 11.4% (5/44), down from 36.4%; revoked
leaks 0. The 10 remaining failures are 6 retrieval misses and 4 generation
errors (wrong arithmetic or units from retrieved evidence), the targets of the
planned `read_range`/`calculate` tools. The gain comes almost entirely from
step 3; steps 1 and 2 were roughly neutral on this set (see Upgrade/05).
Run-to-run noise is about one or two questions. The original 33-question set
stays at retrieval recall@8 100%.

### Extended results after doc 05 steps 4-5 (1 repeat, no judge)

Adds the `read_range`/`calculate` agent tools (not routed), explicit file
scoping, ambiguous-period answers and number normalization. Auto mode: strict
regex accuracy 83.6% (46/55), retrieval recall@8 88.6%, wrongful abstention
about 9-14% run to run, multi_doc 8/9. Forced-mode comparison from the same
work: forced agent 47.3% (26/55) against forced fast 81.8% (45/55), because the
local model almost never called the numeric tools, so numeric routing stayed
off. `sx-fu-actual-vs-budget` (an agent-path question) flips between runs. The
original 33-question set stays at recall@8 33/33 with no wrongful abstention.
